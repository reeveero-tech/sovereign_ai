## السؤال 1: متى فُقد المفتاح الأصلي؟

### الأدلة من الكود

1. **`data/key.secret`** — غير متتبع في git (`.gitignore`). الملف الحالي:
   - مُنشأ: `2026-10-14 06:02` (بعد جلسة الوكيل)
   - الحجم: 43 بايت (مفتاح `token_urlsafe(32)`)
   - صلاحيات: `0600` (المالك فقط)

2. **`data/sovereign_core/ledger.jsonl`** — غير متتبع في git (`.gitignore`):
   - الأحداث 1–11,777: كلها بتوقيعات فاشلة بالمفتاح الحالي
   - أول حدث: `2026-10-14T05:29:11` (قبل إنشاء key.secret الحالي)
   - آخر حدث: `2026-10-14T06:22:35` (بعد إنشاء key.secret الحالي)

3. **git log** — الالتزامات ذات الصلة:
   - `6d4fcfe` — "R-610: persistent sovereign identity — master key survives restarts (data/key.secret)"
   - `213b224` — "fix: real test isolation (SOVEREIGN_DATA_ROOT)..." (أحدث)

### التفسير

المفتاح الأصلي فُقد **قبل** `2026-10-14 05:29:11` (أول حدث في السجل).
كل الأحداث في السجل (11,777) وُقّعت بمفتاح لم يُحفظ (ephemeral key
مؤقت أو مفتاح أُنشئ ثم حُذف). المفتاح الحالي أُنشئ في `06:02` وهو
مختلف عن المفتاح الأصلي.

## السؤال 2: هل فُقد مرة واحدة أم عدة مرات؟

### الأدلة

فحص توزيع التوقيعات الفاشلة (متجاورة زمنيًا أم متقطعة):

- **الأحداث 1–11,777**: كلها فاشلة (لا يوجد أي حدث صالح).
- **التوزيع الزمني**: من `05:29:11` إلى `06:22:35` — متواصلة (لا فجوة).

### التفسير

المفتاح فُقد **مرة واحدة** (وليس عدة مرات). كل الأحداث وُقّعت بمفتاح
واحد أصلي (غير محفوظ)، ثم حُذف/تغيّر، ثم أُنشئ مفتاح جديد مختلف.
لا يوجد دليل على فقدان متعدد (لا توجد فجوات زمنية في التوقيعات الفاشلة).

## السؤال 3: هل `test_persistent_key_survives_restart` موجود في main؟

### الإجابة: **نعم** — موجود ومُصلح.

### الأدلة من git log

```
6d4fcfe R-610: persistent sovereign identity — master key survives restarts (data/key.secret)
e0c374b fix: restore deleted tests, honest death-marker assertion, ...
213b224 fix: real test isolation (SOVEREIGN_DATA_ROOT), original /nexus/recommendations path wired, ...
```

الاختبار موجود في `tests/test_identity_persistence.py` (السطر 48) وقد
أُصلح في الالتزام `213b224` ليعمل في جذر مؤقت معزول (`SOVEREIGN_DATA_ROOT`)
بدل حذف المفتاح الحقيقي.

### لكن: **الاختبار كان هو أداة الجريمة الأصلية**

قبل الإصلاح، كان الاختبار يُنفذ:
```python
if os.path.exists(secret_file):
    os.remove(secret_file)   # ← يحذف المفتاح الحقيقي!
```
ثم يُعيد إنشاء مفتاح جديد. هذا هو السبب الجذري لفقدان المفتاح الأصلي.

**الوضع الحالي**: الاختبار مُصلح (يعمل في جذر معزول، لا يلمس المفتاح
الحقيقي). الباب مُغلق الآن.

## السؤال 4: هل هناك مسار آخر يحذف/يكتب فوق `data/key.secret`؟

### الإجابة: **نعم** — جريمة ثانية مكتشفة.

### الأدلة من الفحص الكامل

فحص كل `os.remove`, `shutil.rmtree`, `Path.unlink()`, `open(..., 'w')`
على مسارات تحتوي `key` أو `secret` أو `data/` في الكود الحي
(باستثناء `emergency_backups`):

| الملف | السطر | ما يفعل |
|-------|-------|---------|
| `tests/test_config_security.py` | 37 | `os.remove(secret_file)` — **يحذف المفتاح الحقيقي** |
| `tests/test_config_security.py` | 54 | `os.remove(secret_file)` — **يحذف المفتاح الحقيقي مرة ثانية** |

### التفاصيل

`tests/test_config_security.py::test_development_without_key_generates_persistent_key`:

```python
# تنظيف أي مفتاح دائم سابق لبدء حالة نظيفة
secret_file = os.path.join(..., "data", "key.secret")
if os.path.exists(secret_file):
    os.remove(secret_file)    # ← يحذف مفتاح التشغيل الحقيقي

first = _run_config(env)      # ← يُنشئ مفتاحًا جديدًا
second = _run_config(env)

# تنظيف بعد الاختبار
if os.path.exists(secret_file):
    os.remove(secret_file)    # ← يحذفه مرة ثانية!
```

**هذا اختبار ثانٍ يحذف المفتاح الحقيقي** — لم يُكتشف في المرحلة الأولى.
هذا يعني الباب ما زال مفتوحًا جزئيًا (اختبار واحد مُصلح، وآخر لا).

### الإجراء المطلوب

يجب إصلاح `tests/test_config_security.py` لاستخدام `SOVEREIGN_DATA_ROOT`
(نفس نمط الإصلاح المُطبق على `test_identity_persistence.py`).

## السؤال 5: هل يكتب الكود على ledger.jsonl بعد فشل التوقيع؟

### الإجابة: **نعم** — لكن هذا ليس جريمة أعمق.

### الأدلة من الكود

`backend/memory/core.py::append_event` (السطر 587):

```python
def append_event(self, event_type, payload, user=None):
    """
    إضافة حدث جديد إلى السجل السيادي.
    لا حذف. لا تعديل. فقط إضافة.
    """
    with FileLock(LOCK_FILE):
        # ... حساب hash + signature ...
        with open(self.log_file, 'a', encoding='utf-8') as f:
            f.write(event_line + '\n')    # ← يكتب دائمًا
```

### التفسير

- **`append_event` يكتب أحداثًا دائمًا** بغض النظر عن حالة التحقق السابقة.
- **هذا سلوك طبيعي وليس جريمة**: السجل إلحاقي (append-only)، والكتابة
  الجديدة لا تعتمد على صلاحية الأحداث القديمة.
- **المشكلة الفعلية**: كل حدث جديد يُوقّع بالمفتاح *الحالي*. عندما يتغير
  المفتاح، كل الأحداث السابقة (الموقعة بالمفتاح القديم) تفشل التحقق
  بالمفتاح الجديد. هذا ليس تزويرًا — إنه فقدان القدرة على التحقق
  (`UNVERIFIABLE_MISSING_KEY`، وليس `INVALID`).

### الخلاصة

النظام يستمر في الكتابة بشكل صحيح. المشكلة ليست في الكتابة، بل في
**فقدان القدرة على التحقق من الأحداث القديمة**. هذا هو الجرح الذي
سيعالجه نظام KeyRing + Merkle Anchoring.
