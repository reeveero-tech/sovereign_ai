## القصة المكتوبة بالسجل

تم بناء النصف الناقص المعلن من البند ٢.٢ (الجولة الموثقة «اللاحقة»): **رفع الصور في الواجهة**. صار للمالك زر «صورة» بجانب الإرسال يفتح منتقي ملفات، والمستخدم يختار صورة، تُفحص محليًا (النوع والحجم — نفس عقد الخادم)، ثم تُرفع multipart إلى `POST /vision`، ويظهر الوصف **في المحادثة نفسها** كرد ذكاء — لا كتابة DOM مجهولة، والتسليم عبر مدخل معلن في chat-runtime.

## قاعدة الإجراءات (والنقل للذات)

كل مسار التغييرات يعتمد على شجرة git الكاملة المستنسخة على `main`؛ ركيزة "تغييرات المالك وحدها" دائمًا. الواجهة الجديدة وحداتها مضافة في نفس الدفعة الذرية (الكود + الاختبار + التوثيق + الحارس)، كما فعلت R-740 — والمادة ٤ (atomic-batch) تُطبق على جميع الالتزامات كما فعلت R-740 وR-739.

### أوجه الميزة الجديدة المضافة في هذه الجولة

هذه الجولة تكمل النصف المكشوف في توثيق ROADMAP_V4 للبند ٢.٢: **واجهة رفع الصور**. لا تغيير في بروتوكول الخادم (R-739 كما هو)، بل الاستهلاك الفعلي من الواجهة:

1. **`frontend/index.html`:** زر `btn-vision-upload` (أيقونة صورة، بجانب النطق في صف المحادثة) + مدخل ملف مخفي `vision-file-input` بقائمة أنواع مطابقة للخادم (png/jpeg/webp/gif/bmp) + تحميل السكربت `js/modules/vision-input.js`.
2. **`frontend/js/modules/vision-input.js` (وحدة جديدة):**
   - فحص محلي صادق قبل أي طلب: النوع من قائمة الخادم نفسها + الحجم ≤ 10MiB — رسائل صادقة بالمرفوضات.
   - رفع `FormData` إلى `POST /vision` (بدون أي رأس تصرف مخصص).
   - صدق كامل لكل رموز عقد الخادم (503/502/413/415/429) — كل واحدة تُعلن بسببها ولا يختلق وصف.
   - استجابة بلا `description` = فشل معلن (لا نجاح كاذب).
   - `input.value = ''` بعد كل اختيار — لا يعلق اختيار سابق.
3. **`frontend/js/modules/chat-runtime.js`:** مدخل `receiveVisionDescription(description, fileName)` معلن — يضيف رسالة مستخدم بصيغة «🖼️ صورة: filename» ثم يمرر الوصف عبر `receiveMessage` (نفس سلسلة رد الذكاء: إضافة، ذاكرة، إشعار، نطق إن كان مفعلًا).
4. **التصنيف:** الزر والمدخل في `control` بقائمة LIVE_BINDINGS (حارس R-730 يرفض غير المصنف)؛ الوحدة مجرودة في INVENTORY كتاسعة وحدة حقيقية تستهلك API (9/78).
5. **حارس الجولة:** `tests/test_vision_ui.py` — 7 اختبارات تحرس الوجود الفعلي (زر + مدخل + تصنيف + وحدة تستهلك النقطة الفعلية وتخاطب الزر والمدخل وتعلن رموز العقد + خطاف المحادثة + تحميل السكربت + الجرد المحدث).

### لماذا هذا الحل يليق بسيادة المالك

- **الإيضاح للمالك قابل للنفي:** لا تعتمد الجولة على أي مصادرة — الرؤية تبقى معطلة بالفعل (VISION_* غير مفعل) وكل زر يظهر رسالة الصدق (503 بالسبب) — لا ادعاء «ناجح» وزر ميت.
- **لا كتابة DOM مجهولة:** التسليم عبر مدخل chat-runtime المعلن (المادة ١ — لا انتحال «تجربة المالك» بأشكال وهمية).
- **مطابقة العقد ثنائية الاتجاه:** قائمة الأنواع في accept الواجهة = قائمة الخادم حرفيًا؛ الحد 10MiB = حد الخادم. أي تغيير مستقبلي في أحدهما يكسر حارس الاختبار لا التطبيق بصمت.
