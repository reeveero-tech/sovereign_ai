# النسخ الاحتياطي والاستعادة — R-847 (D-062، الطبقة ٦)

> كل حالة النظام في مجلد واحد: المفاتيح، والخزنة، والسجل، والطابور، والإشعارات،
> والآثار، وهي على حجم Fly واحد (`sovereign_data` ⇒ `/app/data`). هذه الطبقة تجعل
> فقدان الحجم أو تلفه أو خطأ التشغيل قابلًا للتعافي **بلا ثقة عمياء بالملفات**.

## ما كشفه RED على main

الدليل في `forensics/R-847_backup_RED.txt`، والسكربت في `forensics/R-847_red_script.py.txt`.

| # | العيب | الأثر |
|---|---|---|
| 1 | لا وحدة نسخ للبيانات؛ نسخ الحارس الطارئ يأخذ الكود فقط | لا نسخة أصلًا |
| 2 | `OutboxStore` (اتصال مفتوح لكل خيط): نسخ ملف القاعدة وحده يعطي قاعدة **بلا جدول** | الصفوف كلها في `-wal` (173KB) |
| 3 | استعادة ملف القاعدة وحده مع بقاء `-wal` أحدث | SQLite يعيد تطبيقه: 50 صفًا بدل صف النسخة — استعادة خاطئة صامتة |
| 4 | `/observability/health` لا تفحص أي نسخة | التقادم لا يُرى |
| 5 | حجم واحد، لا موقع ثانٍ | فقدانه = فقدان كل شيء |
| 6 | `GET /backups` ⇒ 404 | لا واجهة |

ملاحظة صدق: `JobStore` نجا من البند 2 صدفةً، لأنه يغلق اتصاله بعد كل معاملة فتُفرَّغ WAL. فالعيب ليس في كل قاعدة، لكن طريقة النسخ الساذجة غير آمنة عمومًا.

## البنية

حزمة `backend/backup/`:

| الوحدة | الدور |
|---|---|
| `snapshot.py` | لقطة متسقة: SQLite (يُعرف **بالرأس** لا بالامتداد) عبر `sqlite3.Connection.backup` ثم `integrity_check`، وjsonl/ndjson/log حتى آخر `\n`، وغيرها نسخ بايتات (كتابات المشروع ذرية) |
| `crypto.py` | AES-256-GCM متدفق بقطع 1MiB. العداد يمنع إعادة الترتيب، وعلم «الأخيرة» يمنع البتر، والرأس AAD، والمفتاح عبر scrypt بملح لكل أرشيف |
| `archive.py` | `tar.gz` أوله `MANIFEST.json` (sha256 وحجم ونوع وصلاحية لكل ملف). التحقق يرفض المسار المطلق و`..` والرابط والجهاز والعضو غير المذكور والمكرر والناقص |
| `catalog.py` | `<id>.svbk` و`<id>.json` (بلا مفتاح أبدًا)، وقفل `flock` غير حاجز، واحتفاظ، و`state.json` |
| `offsite.py` | `DirDestination` (حجم ثانٍ) و`SupabaseStorage` — **مشفر فقط**، ورفع بلا upsert، و401/403 بلا إعادة |
| `restore.py` | خطة جافة، ثم تجهيز بتأكيد، ثم تطبيق عند الإقلاع مع تراجع |
| `service.py` | الإعدادات، والإنشاء، والجدولة، والفحوص، والمقاييس |
| `api_routes.py` | `/backups/*` |
| `__main__.py` | `python3 -m backup apply-pending\|create\|list\|verify <id>` |

### المستثنى من اللقطة

- مجلد الفهرس نفسه (`backups/` أو `SOVEREIGN_BACKUP_DIR`) و`.restore/`.
- ملفات `-wal/-shm/-journal`، لأن محتواها داخل نسخة القاعدة.
- الملفات المؤقتة `.tmp/.part`.
- الروابط الرمزية والملفات الخاصة: تُتخطى، وتُسجل في `manifest.skipped`، ولا تُتبع.

## دورة النسخة

1. أخذ القفل؛ والنسخة المتزامنة تُرفض `busy`.
2. اللقطة إلى `.work/<id>` مع فرض سقف الحجم. التجاوز يعطي `size_cap` بلا بقايا.
3. كتابة الأرشيف إلى `.<id>.svbk.part` مع `fsync`، ثم `os.replace`.
4. **قراءة راجعة كاملة**: تحقق البصمة والوسوم وكل عضو، وإلا يُحذف الأرشيف.
5. الملف الجانبي، ثم الاحتفاظ، ثم الرفع الخارجي إن ضُبط.
6. `state.json` يسجل `last_success` و`last_failure` و`last_offsite`.

كل فشل يُسجل ويُشعر بـ`backup.failed` (high). وفشل الرفع وحده يُشعر بـ`backup.offsite_failed`، ولا يلغي النسخة المحلية.

### الجدولة

خيط مُدار يُدرج كل 300ث مهمة `backup.create` في الطابور بمفتاح `backup:scheduled:<floor(now/interval)>`. النتيجة نسخة واحدة لكل فترة ولو أُعيد الإقلاع. وتحتاج عمال الطابور (`SOVEREIGN_QUEUE_WORKERS>0`).

## الاستعادة (عملية حساسة)

```
POST /backups/{id}/restore/plan        ⇒ added/changed/displaced + plan_hash + confirm
POST /backups/{id}/restore             ⇒ 202 staged
     X-API-Key + Idempotency-Key + {"plan_hash": "...", "confirm": "RESTORE <id>"}
fly machine restart                    ⇒ نقطة الدخول تطبق قبل التطبيق
GET  /backups/restore                  ⇒ pending / last (applied | rolled_back | rollback_failed)
DELETE /backups/restore/pending        ⇒ إلغاء قبل الإقلاع (Idempotency-Key)
```

### لماذا عند الإقلاع؟

قواعد SQLite مفتوحة باتصالات حية، واستبدال ملف تحتها يفسده. فالتجهيز يكتب ملفات متحققًا منها إلى `.restore/staged` ولا يلمس الحالة الحية. ثم `scripts/container_entrypoint.sh` (و`start.sh` محليًا) يشغّل `python3 -m backup apply-pending` **قبل** الحارس والتطبيق.

### الضمانات

- **قبل التجهيز** تُؤخذ نسخة `pre_restore` من الحالة الحالية، وهي محلية لا تُرفع، ولها حد احتفاظ مستقل (3).
- لكل ملف: نسخ إلى مؤقت، ثم `fsync`، ثم `os.replace`. ولقاعدة SQLite تُحذف `-wal/-shm/-journal` **قبل** الاستبدال، فهذا علاج RED البند 3.
- الملفات غير الموجودة في النسخة **تُزاح** إلى `.restore/displaced/<id>/` ولا تُحذف.
- بعد التطبيق تُطابق كل البصمات. وعدم التطابق أو أي خطأ يعني تراجعًا إلى `pre_restore` بالطريقة نفسها، مع إشعار `restore.failed` (critical).
- انهيار وسط التطبيق يترك الحالة `applying`، والإقلاع التالي يعيد التطبيق كله (المصدر المجهز لا يُستهلك). وبعد 3 محاولات يحدث تراجع، فلا حلقة إقلاع.
- فشل التراجع نفسه يترك الحالة `rollback_failed` ظاهرة، ويصير الفحص `backup.restore` failing. والإقلاع **لا يُمنع** حتى يبقى المالك قادرًا على الوصول والتصحيح.

### التعافي من كارثة (فقدان الحجم)

1. حجم جديد فارغ، وإقلاع عادي، مع المفتاح نفسه والوجهة نفسها في الأسرار.
2. `GET /backups/offsite` لاختيار النسخة.
3. `POST /backups/offsite/{id}/fetch` (Idempotency-Key): تنزيل وتحقق كامل، ويُرفض كائن باسم لا يطابق معرّف بيانه.
4. ثم الخطة والتجهيز وإعادة التشغيل كالمعتاد.

## الرصد

- **الفحوص في `/observability/health`**:
  - `backup.freshness`: degraded إن كانت آخر نسخة ناجحة أقدم من ضعف الفترة، أو كانت آخر محاولة فاشلة، أو لم توجد نسخة بعد ضعف الفترة من الإقلاع.
  - `backup.offsite`: degraded عند إعداد غير صالح أو فشل آخر رفع.
  - `backup.restore`: failing إن فشلت استعادة خلال 24س، وdegraded إن وُجدت استعادة مجهزة تنتظر.
- **المقاييس**: `backup_last_success_timestamp` و`backup_archives{kind}` و`backup_bytes` و`backup_offsite_configured` و`backup_restore_pending`.
- **الأحداث**: `backup.failed`، `backup.offsite_failed`، `restore.staged`، `restore.applied` (high)، و`restore.failed` (critical). فشل مهمة `backup.create` لا يُصدر `job.failed` أيضًا (لا إشعاران لسبب واحد).

## الحدود (صراحةً)

1. **لا وجهة خارجية مضبوطة في الإنتاج بعد.** النسخ حتى الآن على الحجم نفسه، فتحمي من التلف وخطأ التشغيل، **لا** من فقدان الحجم. الفحص `backup.offsite` يبقى ok مع سبب صريح والمقياس 0، حتى لا تتكرر الإشعارات كل ساعة. والحل أن يضبط المالك `SOVEREIGN_BACKUP_KEY` ووجهة.
2. **فقدان المفتاح يعني فقدان النسخ المشفرة.** احفظه خارج الخادم. وتدويره يترك النسخ القديمة تحتاج المفتاح القديم، وبصمة `key_fingerprint` تبين أيهما.
3. الاستعادة تحتاج إعادة تشغيل يدوية بعد التجهيز.
4. المساحة: اللقطة تنسخ إلى `.work` ثم تكتب الأرشيف، أي قرابة ضعف حجم البيانات مؤقتًا، والتجهيز يضيف نسخة `pre_restore` ومجلد `staged`. وفحص `disk` يرى ذلك.
5. تنزيل Supabase يحمّل الكائن في الذاكرة (حتى `MAX_MB`)، أما الرفع فمتدفق.
6. ملف غير SQLite وغير ذري يكتبه طرف خارجي لحظة النسخ قد يُلتقط وسط كتابته. أما كتابات المشروع فذرية، وملفات الإلحاق تُقص عند آخر سطر.
7. `plan_hash` يربط القرار بمحتوى النسخة لا بالحالة الحالية، والفرق المعروض إعلامي. والحالة تتغير كل ثوانٍ (السجل)، فربطها يجعل التأكيد مستحيلًا.
8. `.restore/displaced/` لا يُنظف آليًا، لأن الإزاحة عكوسة عمدًا.
9. المقاييس داخل العملية، كبقية R-846.
