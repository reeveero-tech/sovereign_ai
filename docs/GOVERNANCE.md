## 1) القاعدة الحاكمة الوحيدة: الدفعة الذرية

**لا يتم دفع/عمل/دمج أي شيء في المشروع إلا إذا تم في نفس الدفعة تحديث حالة المشروع ووثائقه وخارطة الطريق.**

أي دفعة عمل — commit أو PR أو push أو Batch — يجب أن تحتوي في **نفس الدفعة** على:

1. **التغيير الفعلي**: كود / إعدادات / بيانات / قرار / تحليل / إصلاح.
2. **تحديث ROADMAP.md**: البند الذي عُمل عليه + حالته الجديدة + ما تم + ما تبقى.
3. **تحديث PROJECT_STATE.md**: الحالة الراهنة + المخاطر + العوائق + القرارات.
4. **تحديث الوثائق المتأثرة**: معمارية / API / قاعدة بيانات / تشغيل / أمان / اختبارات.
5. **دليل التحقق**: اختبارات / سجلات / لقطات / نتائج build.
6. **تحديث DECISIONS.md أو ADR** إذا اتخذ قرار مهم.
7. **تحديث CHANGELOG.md** إذا كان المشروع يستخدمه.

### الفرض على الخادم (R-773، 2026-10-26 — بتفويض المالك المطلق D-047)
الرفض لم يعد بعد الدفع بل **عند الدفع نفسه**: قاعدة GitHub على `main` (`tools/github/main_ruleset.json`،
تُطبَّق بـ`tools/github/apply_main_ruleset.sh`) — بلا مستثنين، والمالك منهم:
- لا يُحدَّث `main` إلى التزام لم ينجح عليه فحص `Tests + Atomic Batch Gate` (بوابة الوثائق D-040 + بوابة الحذف + الحزمة كاملة).
- لا force-push ولا حذف للفرع (المادة الثالثة).

**المسار الإلزامي لكل عمل:**
1. التزام واحد ذري (كود + اختبارات + PROJECT_STATE + CHANGELOG + الخارطة النشطة) — حارس pre-commit يرفض محليًا.
2. `git push origin HEAD:work/<البند>` — CI يفحص كل التزام منذ الافتراق عن main.
3. بعد نجاح CI على SHA نفسه: `git push origin HEAD:main` (تقديم سريع بلا دمج ولا rebase).
أي دفع مباشر إلى main بلا فحص ناجح يرفضه الخادم: `push declined due to repository rule violations`.

### ممنوع
- ❌ دفع الكود ثم العودة لدفع التوثيق.
- ❌ دفع الإصلاح ثم دفع تحديث الخارطة.
- ❌ دفع التوثيق في PR منفصل.
- ❌ دمج تغيير دون تحديث الحالة والخارطة.
- ❌ العمل على بند غير موجود في خارطة الطريق (يجوز إضافته، لكن في نفس الدفعة).

### النتيجة عند المخالفة
- الدفعة **مرفوضة**.
- لا دمج، لا دفع، لا احتساب، لا انتقال للبند التالي.

## 4) بوابة CI المقترحة (تُنفَّذ في R-402)

أي PR يغيّر الكود يجب أن **يفشل** إذا:

- لم يغيّر ROADMAP.md.
- لم يغيّر PROJECT_STATE.md.
- غيّر API ولم يغيّر API.md.
- غيّر DB ولم يغيّر DATA_MODEL.md.
- غيّر معمارية ولم يضف ADR.
- لم يرفق دليل تحقق.

### آلية مقترحة (GitHub Actions)
- فحص `git diff --name-only` في الـ PR.
- إذا كان هناك تغيير كود (`backend/`, `frontend/`, `nexus/`, `main.py`, `Dockerfile`, `requirements*.txt`) و **لا** تغيير في `docs/ROADMAP.md` أو `docs/PROJECT_STATE.md` → فشل.
- إذا تغيّر `backend/api.py` أو `backend/app.py` و **لا** تغيير في `docs/API.md` → فشل.
- إذا تغيّر أي ملف بيانات/DB و **لا** تغيير في `docs/DATA_MODEL.md` → فشل.
- إذا تغيّر `backend/orchestrator.py` أو `backend/consciousness/` و **لا** ADR جديد → فشل.

## 6) مراجعة R-601 الدورية

تُجرى المراجعة عند إغلاق كل دفعة وقبل بدء البند التالي:

1. حساب حالات `ROADMAP.md` من البنود نفسها، لا من ملخص قديم.
2. مقارنة `HEAD` المحلي مع `origin/main` وتسجيل أي فرق أو عائق نشر.
3. مطابقة `PROJECT_STATE.md` و`CHANGELOG.md` مع آخر دليل تحقق.
4. منع الانتقال إلى بند جديد إذا كانت الدفعة السابقة غير منشورة أو كانت بوابة atomic-batch غير مكتملة.
5. تسجيل العائق كبند `blocked` مع الخطأ الحرفي وخطوة الإصلاح المطلوبة.

**نتيجة مراجعة 2026-10-13:** تحقق R-601 من أعداد البنود والنشر، وكشف أن R-108 وثّق حد `/chat` دون تطبيقه. أُضيف R-603، واختُبر المحدد (23 اختباراً) ثم نُشر وتحقق التزامن. يبقى المحدد محلياً لكل عملية كما يوثق D-016.

## 8) القاعدة ٨ — الحارس الذاتي (بأمر المالك 2026-10-20، بعد سلسلة R-705/R-707–R-709)

**أي ملف يحتوي حارسًا (regex، قائمة كلمات ممنوعة، نمط فحص) يُعامل معاملة خاصة:**

- **القاعدة ٨ لا تعترف بوسم إعفاء؛ الحل: كتابة حذرة تُبنى وقت التشغيل.** الأمثلة والأنماط
  الحرفية داخل الحارس تُبنى برمجيًا (تجميع الأجزاء بالتسلسل أو بـ `chr()`)، مثل قواعد النطاقات في
  `tools/private_ip_guard.py` (GS-3).
  > السبب (قرار المالك ٤.١٢-ب، SEC-2): سلسلة R-705→R-709 ثم GS-3 أثبتت أن الكتابة الحذرة تكفي
  > في كل حالة واجهناها، وأن الاستثناء خطر: وسمٌ يُعفي سطرًا من الحارس قد يصير ثغرة تسريب. ولم
  > يدعم أي حارس الوسم قط، فكان وعدًا لا يعمل. أي وسم يُكتب يبقى بلا أثر، والحارس يفحص السطر كاملًا.
- البديل الأنظف: يُفحص الحارس بمثال من ملف آخر (اختبار يكتب المثال في ملف مؤقت أو
  مستودع تجريبي)، لا بأمثلة حية داخل ملفه.
- ترتيب الالتزام الصارم لأي جولة يُنتج نصوصًا يفحصها حارس: (1) كتابة كل النصوص؛
  (2) `git add` للملفات المقصودة؛ (3) تشغيل الحارس والتحقق من رمز خروجه الفعلي؛
  (4) الالتزام دون تعديل بعده.
- الهدف: منع المفارقة الذاتية — الحارس الذي يمسك أمثلته يفشل البناء بلا سبب حقيقي.
- **أتمتة الخطوة (3) — hook محلي (GS-3، قرار المالك د.٣):** `.githooks/pre-commit` يشغّل
  `tools/private_ip_guard.py --staged` على محتوى الفهرس قبل كل التزام، ويرفضه برمز 1 عند أي
  عنوان خاص. التفعيل مرة لكل استنساخ: `git config core.hooksPath .githooks`. حدّ معلن: يمكن
  تجاوزه بـ `--no-verify` — البوابة الصلبة تبقى اختبار CI. **مثبت:** الـhook أمسك نواة الحارس
  نفسها أثناء كتابتها (ملف غير متتبع بعد — فجوة R-705 ذاتها) قبل أن يراها اختبار الملفات المتتبعة.
