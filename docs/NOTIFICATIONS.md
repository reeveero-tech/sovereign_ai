## 1) لماذا

بعد R-844 صارت الحلقات تعمل في الخلفية. لكن المالك لا يعلم أن حلقة تنتظر
موافقته، أو أن كتابة انقطعت وتحتاج مراجعته، إلا إذا استطلع `/orchestrator`
أو `/queue` يدويًا. الدليل في `forensics/R-845_notifications_RED.txt`.

الحالة الأخطر هي `needs_owner_review`، وهي نتيجة كتابة غير مؤكدة. النظام
يمتنع عن إعادتها عمدًا (D-059)، فإن لم يعلم المالك بها تبقى معلقة بلا نهاية.

## 2) البنية

```
المنسق._finalize ──observers──▶ events.from_loop ─┐
العامل.run_once ──FINISH_HOOKS─▶ events.from_job ─┼─▶ service.emit ─▶ الصندوق (SQLite)
POST /notifications/test ─────────────────────────┘          │
                                                            ▼
                                   الموزع (خيط مستقل) ─▶ webhook / telegram
```

- **الصندوق الداخلي** هو جدول `notifications`. يعمل دائمًا ويستقبل كل الشدات،
  ولو لم تُضبط أي قناة خارجية.
- **مفتاح عدم التكرار** (`dedupe_key`) يُشتق من الحدث، فالحدث نفسه لا يُنشئ
  إشعارين. الأمثلة: `approval.requested:{approval_id}`، و`review.required:{loop_id}`،
  و`job.dead:{job_id}`.
- **تسليم واحد لكل (إشعار، قناة)**. حالات التسليم:
  - `pending`: مستحق للإرسال.
  - `sent`: أُرسل.
  - `failed`: فشل نهائيًا.
  - `suppressed`: كُبت بسبب حد الساعة.
  - `skipped`: القناة غير مضبوطة أو الشدة تحت حدها، مع تسجيل السبب.
- **الموزع مستقل عن الطابور**: إشعار «مهمة ميتة» لا يصح أن يعتمد على الطابور نفسه.
- **الإصدار لا يكسر المُصدِر**: المراقب المعطوب يُسجَّل في السجل، والحلقة أو
  المهمة تكمل (N11).
- **لا إشعاران لسبب واحد**: فشل مهمة مرتبطة بحلقة يغطيه إشعار `loop.failed`
  وحده (N13).

## 3) الأحداث

| الحدث | الشدة | متى |
|---|---|---|
| `review.required` | حرجة | انقطاع أثناء كتابة، فلا إعادة (D-059) |
| `approval.requested` | عالية | حلقة تنتظر موافقة |
| `job.dead` | عالية | مهمة استُنفدت محاولاتها |
| `eval.failed` | عالية | `evaluation.run` تحت الأرضية |
| `notify.test` | عالية | `POST /notifications/test` |
| `clarification.needed` | متوسطة | الحلقة تحتاج توضيحًا |
| `loop.failed` | متوسطة | فشلت حلقة |
| `job.failed` | متوسطة | فشلت مهمة غير مرتبطة بحلقة |

**أقل بيانات**:
- القنوات الخارجية تتلقى الحقول `id` و`event` و`severity` و`title` و`summary`
  و`link` و`created_at` فقط.
- نص الرد الكامل (`body`) يبقى في الصندوق الداخلي.
- نص الطلب الأصلي لا يغادر الخادم (N01).
- كل نص يُنقّى من أنماط الأسرار قبل الحفظ والإرسال (N14). الأنماط المشمولة:
  `ghp_` و`github_pat_` و`sbp_` و`rnd_` و`sk-` و`xox*-` و`Bearer` ورمز بوت Telegram.

## 4) القنوات

| القناة | الإعداد | الضمانات |
|---|---|---|
| `webhook` | `SOVEREIGN_NOTIFY_WEBHOOK_URL` (يجب أن يبدأ بـ`https://`) + `SOVEREIGN_NOTIFY_WEBHOOK_SECRET` (16 حرفًا على الأقل) | `X-Sovereign-Signature: sha256=HMAC(secret, ts + "." + body)` و`X-Sovereign-Timestamp`. `Idempotency-Key` = معرّف الإشعار، فيستطيع المستقبِل إسقاط التكرار. بلا https أو بلا سر لا يحدث أي إرسال (N07) |
| `telegram` | `SOVEREIGN_TELEGRAM_BOT_TOKEN` + `SOVEREIGN_TELEGRAM_CHAT_ID` | نص خام بلا `parse_mode`. الرمز موجود في الرابط فقط، لذلك رسائل أعطال الشبكة لا تحمل الرابط، والرمز لا يظهر في نص الرسالة (N03) |

**التحقق من التوقيع عند المستقبِل** (مثال بايثون):

```python
want = hmac.new(secret, ts.encode() + b"." + raw_body, hashlib.sha256).hexdigest()
ok = hmac.compare_digest(header_sig, "sha256=" + want) and abs(time.time() - int(ts)) < 300
```

## 5) سياسة الإرسال

| الحالة | ماذا يحدث |
|---|---|
| 2xx | `sent` |
| 401 أو 403 | `failed` بلا إعادة، **وتُعطَّل القناة** ببصمة إعدادها، فلا يتكرر الطرق على باب مغلق (N04). يُرفع التعطيل تلقائيًا إذا تغيّر الإعداد (تدوير الرمز)، أو يدويًا عبر `POST /notifications/channels/{name}/enable` |
| 4xx أخرى | `failed` نهائي |
| 408 أو 425 أو 429 أو 5xx أو عطل شبكة أو مهلة | إعادة بتأخير 5 ثم 10 ثم 20 ثانية وهكذا (السقف 600ث)، بحد 5 محاولات ثم `failed` (N05، N06) |
| خطأ برمجي غير متوقع | `failed` بلا إعادة عمياء |
| حد الساعة (`SOVEREIGN_NOTIFY_MAX_PER_HOUR`، افتراضيًا 30 لكل قناة) | الزائد `suppressed`، ويبقى في الصندوق الداخلي (N09) |
| انقطاع بعد الإرسال وقبل التسجيل | بعد انتهاء الإيجار (60ث) يُعاد الإرسال **بنفس `Idempotency-Key`**، وهذا ضمان أقل مرة واحدة معلن (N10). عدد الانقطاعات محدود بـ`MAX_ATTEMPTS` |
| شدة تحت حد القناة | `skipped`، والإشعار في الصندوق الداخلي فقط (N08) |

**الشدة**:
- الحد الافتراضي للقنوات الخارجية `high`، ويُضبط عبر `SOVEREIGN_NOTIFY_MIN_SEVERITY`.
- لكل قناة حد خاص اختياري: `SOVEREIGN_NOTIFY_WEBHOOK_MIN_SEVERITY` و`SOVEREIGN_NOTIFY_TELEGRAM_MIN_SEVERITY`.

## 9) حدود صادقة

- **Telegram لا يدعم مفتاح عدم تكرار**. إعادة الإرسال بعد مهلة غامضة قد تكرر
  الرسالة، وهذا ضمان أقل مرة واحدة. اخترتُ ذلك عمدًا: تكرار إشعار أهون من ضياع
  طلب موافقة أو مراجعة حرجة.
- **لا قناة بريد أو SMS أو دفع للجوال بعد**. Webhook الموقّع يغطيها عبر وسيط
  يملكه المالك.
- **الإشعارات لا تحمل أزرار موافقة**: الموافقة تبقى عبر الواجهة المصادَق عليها.
  لا موافقة من رابط في رسالة، لأن ذلك يتجاوز البوابة.
- **مسار `/orchestrator/loops` المتزامن** يُصدر الإشعارات أيضًا، لأن المراقب في
  `_finalize`. أما الحلقة التي تُنشأ بمنسق غير المنسق المشترك (مثل الاختبارات)
  فلا تُصدر إلا إذا رُبط بها مراقب.
- **التخزين**: SQLite على القرص المحلي. بقاء البيانات عبر النشرات يتوقف على قرص
  Render الدائم.
- **لم تُضبط أي قناة خارجية في الإنتاج بعد**. القرار والإعداد للمالك، وحتى
  ذلك الحين الصندوق الداخلي وحده يعمل.
