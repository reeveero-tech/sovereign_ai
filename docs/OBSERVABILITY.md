# OBSERVABILITY.md — الرصد (R-846، D-061)

> آخر تحديث: 2026-11-04 (R-846)

## 1) لماذا

بعد R-844 وR-845 صارت الحلقات تعمل في الخلفية والإشعارات تُرسل. صار ممكنًا أن يتعطل شيء دون أن يراه أحد. فحص RED على main (`forensics/R-846_observability_RED.txt`) كشف ستة عيوب:

| # | العيب | الدليل |
|---|---|---|
| 1 | أثر الحلقة يضيع بعد إعادة التشغيل | `trace()` ⇒ «لا أثر لهذه الحلقة» |
| 2 | المتتبعات تتضخم بلا حد | 300 متتبع في الذاكرة بعد 300 حلقة |
| 3 | `/health` «healthy» ثابتة | لا ترى الطابور ولا الإشعارات |
| 4 | لا معرّف طلب | لا `X-Request-ID` في الردود |
| 5 | لا مقاييس | `/metrics` ⇒ 404 |
| 6 | سر في السجل | `ghp_…` في رسالة سجل يمر كما هو |

ملاحظة صدق عن العيب 3: العمال كانوا 0 في الاختبار لأن خيوط الخلفية معطلة هناك. العيب أن النقطة لا تنظر إليهم أصلًا.

## 2) البنية — `backend/observability/`

| الملف | الدور |
|---|---|
| `redact.py` | نمط أسرار واحد للسجلات والآثار ووسوم المقاييس |
| `context.py` | `request_id`/`loop_id`/`job_id` عبر contextvars، و`bind()` |
| `metrics.py` | سجل Counter/Gauge/Histogram، سقف السلاسل، جامعون، صيغة Prometheus |
| `logs.py` | مصنع سجلات منقّي، ومرشّح للاستثناءات، و`JsonFormatter` |
| `http.py` | وسيط ASGI خالص: معرّف الطلب ومقاييس HTTP بقالب المسار |
| `health.py` | فحوص خالصة بتبعيات محقونة، و`HealthWatcher` |
| `service.py` | ربط الرصد بالمنسق والطابور والإشعارات، وتشغيل المراقب |
| `api_routes.py` | `make_router()`: `/metrics` و`/observability/health` و`/observability/summary` |

قاعدة الربط: **الرصد لا يكسر ما يرصده**.
- الجامع المعطوب يُعدّ في `obs_collector_errors_total` وتستمر القراءة (O19).
- فشل ربط الرصد عند الإقلاع يُعلن في السجل والخادم يعمل.
- فشل كتابة الأثر لا يكسر الحلقة.

## 3) المقاييس

| المقياس | النوع | الوسوم |
|---|---|---|
| `http_requests_total` | counter | `method`, `route` (قالب)، `status` |
| `http_request_duration_seconds` | histogram | `method`, `route` |
| `orchestrator_loops_total` | counter | `status` (عند كل انتظار/نهاية) |
| `queue_jobs_finished_total` | counter | `kind`, `status` |
| `queue_jobs`، `queue_depth`، `queue_max_depth`، `queue_oldest_queued_age_seconds`، `queue_workers_alive` | gauge (جامع) | `status` لـ`queue_jobs` |
| `notify_deliveries`، `notify_unread`، `notify_channels_disabled`، `notify_dispatcher_running` | gauge (جامع) | `status` لـ`notify_deliveries` |
| `obs_health_status` | gauge (جامع) | `check` — 0 سليم، 1 متدهور، 2 فاشل |
| `obs_series_overflow_total`، `obs_collector_errors_total` | counter | `metric` / `collector` |
| `process_uptime_seconds`، `process_threads` | gauge | — |

- **وسم المسار هو القالب** (`/orchestrator/loops/{loop_id}`) لا القيمة. ما لا يطابق أي مسار يُوسم `__unmatched__`، فلا يفجّر المسح عدد السلاسل (O03، O04).
- **سقف السلاسل**: 200 سلسلة لكل مقياس. الزائد يُجمع في سلسلة `__overflow__` ويُعدّ في `obs_series_overflow_total` (O05).
- قيم الوسوم تُنقّى وتُهرَّب وتُقص إلى 120 حرفًا.
- **حد صادق**: المقاييس داخل العملية تُصفَّر عند إعادة التشغيل. هذا يخص العدادات فقط. الجامعون يقرؤون المخازن الدائمة، فلا يتأثرون.

## 4) السجلات

- **تنقية عند المصدر**:
  - المصنع يحسب نص الرسالة وينقّيه، ثم يجعل `args=()`. بذلك لا يرى أي معالج القيم الخام.
  - المرشّح على معالجات الجذر ينقّي نص الاستثناء والمكدس (O08).
- **الأنماط المنقّاة**:
  - `ghp_`/`gho_`/`ghs_`/…، و`github_pat_`، و`sbp_`، و`rnd_`، و`sk-`، و`xox*-`، و`Bearer`، ورمز بوت Telegram.
  - أزواج مثل `password=`/`token:`/`api_key=`.
- **الربط**: كل سجل داخل طلب HTTP يحمل `request_id`. و`bind(loop_id=…, job_id=…)` يضيف معرّفي الحلقة والمهمة.
- **JSON**: `SOVEREIGN_LOG_FORMAT=json` يجعل كل سطر JSON بالحقول التالية: `ts`، `level`، `logger`، `msg`، `request_id`، `loop_id`، `job_id`، `exc` (O09).
- التثبيت متكرر بأمان (idempotent).

## 5) معرّف الطلب

- `X-Request-ID` الوارد يُحفظ إن طابق `^[A-Za-z0-9._-]{8,64}$`، وهذا يربط الطلب عبر الخدمات.
- غير ذلك يُستبدل بمعرّف `uuid4` (32 حرفًا) (O01، O02).
- يُعاد المعرّف في رأس كل رد ويرتبط بكل سجل أثناء الطلب.
- الوسيط ASGI خالص، لا `BaseHTTPMiddleware`: لا يلمس جسم الرد ولا يكسر البث.

## 6) الآثار الدائمة

راجع docs/ORCHESTRATOR.md §14. باختصار:
- ملف ذري لكل حلقة تحت `traces/`.
- الاستعادة بعد إعادة التشغيل تكمل الأثر نفسه (O10، O12).

## 7) الجاهزية

`GET /observability/health` مفتوحة وتعيد `{status, checks[], ts}`. الحالة الكلية هي أسوأ فحص. عند `failing` تعيد 503.

| الفحص | متدهور | فاشل |
|---|---|---|
| `queue.store` | — | المخزن لا يُقرأ |
| `queue.depth` | العمق/السقف ≥ 90% | — |
| `queue.workers` | — | عمال متوقعون وأحدهم ميت أو لا عامل |
| `queue.dead_jobs` | مهام ماتت في آخر ساعة | — |
| `notifications.dispatcher` | — | موزع متوقع وليس حيًا |
| `notifications.channels` | قناة معطلة آليًا (مثل 401) | — |
| `notifications.backlog` | أقدم تسليم معلّق أكثر من 600ث | — |
| `disk` | الحر أقل من 5% | الحر أقل من 1% |

- **«متوقع»** يعني ثلاثة شروط معًا:
  - بدأ الإقلاع.
  - خيوط الخلفية مسموحة.
  - عدد العمال أكبر من 0، أو `SOVEREIGN_NOTIFY_DISPATCH` لا يساوي 0.
- في الاختبارات حيث الخيوط معطلة، غياب العمال ليس فشلًا. هذا مصرّح به في سبب الفحص.
- `/health` القديمة **لم تتغير**، فهي فحص حياة لـRender. لو صارت 503 عند تدهور الطابور لأعاد Render تشغيل الخدمة بلا داعٍ.

**المراقب** (`HealthWatcher`):
- يدور كل `SOVEREIGN_HEALTH_WATCH_S` ثانية (الافتراضي 60، والقيمة 0 تعطله).
- يحوّل كل فحص غير سليم إلى إشعار: `health.failing` حرج، و`health.degraded` عالٍ.
- مفتاح عدم التكرار `health.{status}:{check}:{ساعة}`، فيصل العطل المستمر مرة واحدة في الساعة (O17).
- دورة فاشلة تُسجَّل والمراقب يكمل.

## 10) حدود صادقة

- لا تتبع موزع عبر الخدمات (OpenTelemetry). المعرّف يُمرَّر ويُسجَّل فقط.
- المقاييس لعملية واحدة. تعدد العمليات يحتاج جامعًا خارجيًا يجمع كل نسخة.
- لا لوحة عرض مدمجة. `/observability/summary` لقطة JSON، والصيغة النصية جاهزة لأي جامع Prometheus.
- فحص القرص يقيس مجلد البيانات. لا يقيس الذاكرة ولا وحدة المعالجة.
